# ProgressBar

`ProgressBar` is a non-interactive track-and-fill indicator showing progress toward a value. It follows the shared conventions in [Components](../index.md).

## Public API

- `ProgressBarProps` composes `IntentElementProps`, `ScalableElementProps`, `SizeElementProps`, `PositionElementProps`, `ZIndexElementProps`, and `React.InstanceProps<ImageLabel>`, plus:
  - `value: number` (required) — the current progress amount.
  - `max?: number` (default `100`) — the value representing full progress. `value` is clamped to `[0, max]` before being normalized; a `max` of `0` (or negative) renders an empty fill instead of dividing by zero.
  - `intent?: Intent` — selects the fill's color scheme (default `"primary"`), the same semantic-color knob `Checkbox`/`Button`/`Pagination` use; there is no hover/focus state since the component isn't interactive.
  - `scale?: ScaleSize` — selects the track's height from `theme.components.progressBar.height` (keyed the same way `Icon`'s `theme.iconSize` is), default `theme.default.scale`; also selects the header row's spacing/typography entries when a header is present (see below).
  - `label?: string` — optional text shown at the start (left) side of a header row above the track. Omitted by default, in which case no header row renders at all (not even an empty one).
  - `showValue?: boolean` — when `true`, renders a formatted value at the end (right) side of the header row, opposite `label`. Works independently of `label` — setting only `showValue` renders a header row with just the right-aligned value and nothing on the left.
  - `valueFormatter?: (value: number, max: number) => string` — optional custom formatter for the displayed value, called with the same clamped `value`/`max` pair used to compute the fill's progress. Defaults to a rounded percentage string (`` `${math.round(percent)}%` ``, e.g. `"30%"`) based on `clampedValue / maxValue`, matching how the component already computes its fill's `targetProgress`.
  - `striped?: boolean` — overrides `theme.components.progressBar.fill.stripe.enabled` (theme default is `false` in every shipped theme). When the resolved value is `false`, there is zero visual/behavioral difference from a plain bar — no overlay element renders and no stripe animation runs.
  - `stripeDuration?: number` — overrides `theme.components.progressBar.fill.stripe.duration` (component fallback `0.75`) when neither the prop nor the theme set it. Seconds for one full tile-width animation loop; lower is faster.
  - `stripeDirection?: number` — overrides `theme.components.progressBar.fill.stripe.direction`. `1` sweeps left-to-right, `-1` sweeps right-to-left. Resolution is defensive rather than a plain `??` fallback: the merged value (`stripeDirection` prop, else the theme's `direction`) is treated as `-1` only when it is *exactly* `-1`; every other value — including `1`, `undefined`, `0`, or anything else — resolves to `1`. Component fallback is therefore effectively `1`.
- `ProgressBar` forwards a ref to the underlying track `ImageLabel` — it's a thin wrapper around [`Container`](../layout/container.md) (like `Box`), so a ref typed `React.useRef<Frame>()` will not type-check against it. This holds whether or not a header row is rendered: the ref always targets the track specifically, never a header-wrapping element.
- The track always spans the full available width (`SizeHelper.GetSize(props, new UDim2(new UDim(1, 0), height))`); only the height is theme/`scale`-driven by default, matching `Slider`'s "explicit height, full-width track" convention. `width`/`Size`/position props override this the same way they do on any `SizeElementProps`/`PositionElementProps` component.
- When `label` and/or `showValue` produce a header row, the component's render tree gains one extra wrapping frame around `[header row, track]` (vertically stacked, full width, auto-height) so `Position`/`AnchorPoint`/`top`/`left`/`right`/`bottom`/`center`/`ZIndex` from `PositionElementProps`/`ZIndexElementProps` apply to that wrapper instead of directly to the track. With no `label`/`showValue`, the component renders exactly the bare track as before (no wrapper, no behavior change) — the wrapper only exists when a header is actually shown.

## Behavior

- The track (`Container` root) renders `theme.components.progressBar.track`'s background/border/corner styling, clips its descendants, and contains a single `Fill` child frame.
- The fill's width animates from its previous scale to `value / max` (clamped to `[0, 1]`) over `theme.components.progressBar.animation.duration` seconds via `@rbxts/react-ripple`'s `useTween`, the same "tween the width, `0` duration snaps instantly" idiom `Switch` uses for its thumb position. Repeated `value` changes continue the tween smoothly from its current position rather than restarting.
- The fill's color (and optional gradient) is resolved via `ColorHelper.getIntentColors(theme, props.intent, "default", theme.components.progressBar.fill.intents)` — only a `"default"` state exists, there is no hover/disabled treatment.
- When rendered, the header row is a single `HStack` with `HorizontalFlex={Enum.UIFlexAlignment.SpaceBetween}`, so `label`'s `Text` (if present) sits flush left and the formatted value's `Text` (if present) sits flush right, with any remaining width left empty between them — there is no visible connector between the two. The header row sits above the track with `theme.components.progressBar.header.spacing` of vertical gap (resolved via `props.scale`, the same "component map overrides the global map per-key" tier `SpacingHelper.GetPadding` uses elsewhere).
- **Stripe overlay.** When the resolved `striped` value is `true`, the fill segment (`ClipsDescendants={true}` unconditionally, harmless when no stripe is present) gains a tiled `ImageLabel` overlay covering it end to end. The overlay is one tile wider than the fill (`Size = UDim2(1, tileWidth, 1, 0)`) and its `Position.X.Offset` is swept by a `@rbxts/react-ripple` `useTween` (`linear` easing, `repeats: math.huge`, `reverses: false`) that loops from `0` to `1` over `stripeDuration` seconds, restarting from `0` whenever `striped` becomes `true` (or `stripeDuration` changes) so the tween is only running while the stripe is visible:
  - resolved `stripeDirection` of `1` maps tween progress `0..1` to `Position.X.Offset` `-tileWidth..0` (increasing, so the pattern appears to travel rightward).
  - resolved `stripeDirection` of `-1` maps the same `0..1` progress to `Position.X.Offset` `0..-tileWidth` (decreasing, leftward).
  - `tileWidth` is the resolved stripe image's `TileSize.X.Offset` (via `CssHelper.resolveBackgroundImage(theme.components.progressBar.fill.stripe.image)`), falling back to `16` if the theme doesn't set a tile size (or doesn't set `image` at all). Because the overlay is exactly one tile wider than the fill and slides by exactly one tile width per loop, the seamless tiling reads as continuous unbroken motion with no visible seam or reset-snap.
  - The overlay's `Image`/`ImageColor3`/`ImageTransparency` come from the same resolved `theme.components.progressBar.fill.stripe.image` (an `Omit<Partial<CssBackgroundImage>, "size">`, the same shape `track.backgroundImage` uses elsewhere in this theme minus `size`), with `ImageTransparency` falling back to `0.9` if unset and `Image` falling back to a built-in default stripe asset if `image` is unset entirely (so `enabled: true` with no `image` configured still renders something rather than a broken image). `ScaleType` is always forced to `Enum.ScaleType.Tile` in code, unconditionally — the theme's `image` config has no `size`/`ScaleType` field at all, since a repeating stripe overlay only ever makes sense tiled. This forced-`Tile` scale type is also a deliberate workaround for a Roblox engine limitation where `ImageRectOffset` is ignored under `ScaleType.Tile`, which is why the sweep is implemented by animating the tiled image's `Position` rather than its `ImageRectOffset`.

## Theme

`theme.components.progressBar` supplies:

- `height` — a `ScaleSizeValue<CssSize>` (one entry per `scale` key) for the track's default height.
- `animation.duration` — the fill-width tween duration; `0` disables the animation (the fill jumps to the new width instantly).
- `track.backgroundColor`, `track.backgroundTransparency`, `track.borderColor`, `track.borderThickness`, `track.cornerRadius` — the track's fixed appearance, plus optional `track.backgroundImage`/`track.backgroundGradient` (same `CssBackgroundImage`/`CssBackgroundGradient` shapes `Box` uses) for a themed texture/gradient layered under the fill.
- `fill.cornerRadius` — the fill segment's own corner rounding (independent of the track's).
- `fill.intents` — per-`Intent` color overrides (`default` state only, including its `backgroundGradient`) layered on top of `theme.colors.intents` for the fill, resolved the same three-tier way every other themed component's `intents` map is (see [Components](../index.md#theming)). All shipped themes explicitly define all five intents (`primary`, `success`, `info`, `warning`, `danger`) here, tuned as saturated fill colors — never leave only `primary` defined, since `ColorHelper.getIntentColors` always layers the component theme's `primary` entry in as a shared-fallback tier before the requested intent's own entry, so an intent left undefined here would silently render using `primary`'s override color instead of falling back to `theme.colors.intents.<intent>.default`.
- `fill.stripe` (optional) — the diagonal-looking tiled-stripe overlay described above. Only `enabled` is required; `image`/`duration`/`direction` are all optional, since a theme that ships `enabled: false` shouldn't have to also fill in stripe visuals/timing for a stripe that's off. Setting `enabled: true` with none of the other fields set still renders (falling back to the component's built-in defaults for each) rather than crashing, though nobody would realistically enable it without also giving it an `image`:
  - `enabled: boolean` (required) — the theme-level default for `striped`; every shipped theme ships this `false` (opt-in only, via the `striped` prop).
  - `image?: Omit<Partial<CssBackgroundImage>, "size">` — the stripe's asset id, tile size, and transparency/tint, using the same `CssBackgroundImage` shape (and `CssHelper.resolveBackgroundImage` resolution) `track.backgroundImage` uses, minus `size`/`ScaleType` — the overlay's scale type is always forced to `Tile` in code (see above), so it isn't part of this theme field at all. Every shipped theme reuses asset `86644568183933` with `tileSize: "16px"`, with `transparency` tuned per theme so the stripe reads well against that theme's fill colors.
  - `duration?: number` — the fill-stripe sweep's one-tile-width loop duration in seconds, named consistently with the sibling `animation.duration` field; every shipped theme uses `0.75` (wooden uses `0.85`). Component fallback when unset is `0.75`.
  - `direction?: number` — the sweep's default direction; `1` for left-to-right, `-1` for right-to-left, defensively normalized as described under `stripeDirection` above (anything other than exactly `-1` behaves as `1`). Every shipped theme uses `1`.
- `header.spacing` — a `ScaleSizeValue<number>` (one entry per `scale` key, resolved via `SpacingHelper.GetPadding`) for the vertical gap between the header row and the track. Only used when a header row actually renders.
- `header.label.typography` — the `label` text's typography (a plain `Partial<TypographyStyle>` override, or a `ScaledTypographyStyle` keyed per `scale`), resolved via `TypographyHelper.getTypography(theme, props.scale, ...)` the same way every other themed component's optional typography override is. The `label` text's color comes from this typography's own `color` field (`TypographyStyle.color`) rather than a separate color key — the resolved typography is passed straight through to `Text` as both its `typography` prop and (via `.color`) its `TextColor3`.
- `header.value.typography` — the formatted value text's typography; falls back to `header.label.typography` (the whole object, not merged field-by-field) when unset, resolved the same way as `header.label.typography`, including its `color` field for the value text's color.

## Story

Worth demonstrating: a determinate bar animating between a few values, the `max` prop with a non-default value, a few `intent` variants side by side, a `label`+`showValue` header row (including the `showValue`-only, no-`label` case and a custom `valueFormatter`), and the `striped` overlay (including both `stripeDirection` values and a couple of `stripeDuration` speeds) layered on top of an animating bar.
