# Card

`Card` groups related content behind a bordered `Box` surface, with optional `Header`, `Body`, and `Footer` sub-parts that share a common `intent`. It follows the shared conventions in [Components](../index.md).

## Public API

- `CardProps extends BoxProps, IntentElementProps`. `Card` forwards a ref to the underlying `Box`'s `ImageLabel`.
- Sub-parts: `Card.Header` (`CardHeaderProps extends IntentElementProps, PositionElementProps, ZIndexElementProps, SpacedElementProps`, plus `children`, `overlay?: boolean`, `padding?: CssPadding`, and `resolvedPadding?: ResolvedPadding`), `Card.Body` (`CardBodyProps extends BoxProps` — inherits the full padding prop set through `BoxProps`), `Card.Footer` (`CardFooterProps extends IntentElementProps, BoxProps`, plus `overlay?: boolean`, `padding?: CssPadding`, and `resolvedPadding?: ResolvedPadding`). None of these sub-part prop interfaces are exported. `Card.Header`/`Card.Footer` deliberately don't extend the full `PaddingProps` — they already use `top`/`left`/`right`/`bottom` (via `PositionElementProps`) for overlay positioning, so only `spacing`, `padding`, and `resolvedPadding` are exposed as padding tier-4 overrides on those two sub-parts; there is no per-side (`top`/`bottom`/`left`/`right`) padding override on the header/footer, only the whole-quad `padding`.
- `Card.Header`/`Card.Footer`/`Card.Body` are ordinary composed children in the common case — a consumer places them directly as JSX children and they render in place. However, `Card` *does* walk its direct `children` (via `React.Children.forEach`/`React.isValidElement`, matching `child.type === CardHeader`/`=== CardFooter`) to find at most one `Card.Header` and one `Card.Footer` that resolve to "overlay" mode (see below) so it can pull that element out of the normal flow — this is the same extraction technique `Accordion` uses for its items, applied narrowly (only overlay-requesting header/footer are ever pulled out; everything else, including a non-overlay `Card.Header`/`Card.Footer`, stays exactly where the consumer placed it).

## Intent inheritance

- `Card` provides a `CardContext` (`{ intent?: Intent }`) to its subtree with its own `intent` prop.
- `Card.Header` and `Card.Footer` each resolve their intent as `props.intent ?? card.intent ?? "primary"` — an `intent` set directly on the header/footer overrides the card-level intent for that section only.
- `Card.Body` has no intent concept; it renders plain padded content.
- The outer `Box`'s border color always comes from the *header's* resolved intent (`ColorHelper.getIntentColors(theme, props.intent ?? "primary", "default", theme.components.card.header.intents)`), even when the card has no `Card.Header` child — there is no separate top-level card border color.

## Composition

- `Card` always renders a `Box` with `spacing="None"` and `center={undefined}` forced (any `center` prop passed to `Card` is not applied to the inner `Box`), wrapping a `VStack` (`spacing="None"`) of the non-overlay `children` (in their original order).
- `center={true}` on `Card` (only when `Position`/`AnchorPoint` are not also supplied) instead wraps the `Box` in an outer full-size `Container` with a horizontally/vertically centering `uilistlayout` — centering is implemented at the wrapper level, not by `Box` itself.
- `Card.Header` renders a `Container` with background/border from its resolved intent, padding resolved through the shared tiered [padding resolution](../index.md#padding-resolution) against `theme.components.card.header.spacing`/`.padding` — pinned to the `"md"` scale key by default (see Theme below) — and only its top corners rounded (`theme.components.card.cornerRadius`). It also passes its resolved intent's `backgroundImage` straight through to that `Container`.
- `Card.Footer` mirrors `Card.Header` but rounds only its bottom corners and resolves padding against `theme.components.card.footer.spacing`/`.padding`/`footer.intents`.
- `Card.Body` wraps its content in a `FlexItem` so it grows to fill remaining vertical space in the card. Its padding resolves independently through the shared tiered padding resolution against its own theme node — `theme.components.card.body.spacing` (tier 2) and `theme.components.card.body.padding` (tier 3, type `ScaledCssPadding`) — rather than falling back to `theme.components.box.padding`; `Card.Body` wraps its children in a plain `Container`, not a `Box`, so it never inherits `Box`'s own padding tiers "for free." A caller overrides with any of the standard padding props (`spacing`, `top`/`bottom`/`left`/`right`, `padding`, `resolvedPadding`, via `BoxProps`), merged per side against these tiers rather than resetting the whole quad.
- `Card.Header` and `Card.Footer` resolve their border stroke `Thickness` as `theme.components.card.header.borderThickness ?? theme.components.card.borderThickness` (and the footer equivalent) — an optional per-section override that falls back to the shared card-level thickness. Every shipped theme today leaves the per-section override unset, so the effective thickness is always `theme.components.card.borderThickness`.

### Overlay placement

A `Card.Header`/`Card.Footer` is in "overlay" mode when `props.overlay ?? (theme.components.card.header/footer.position?.position === "absolute")` resolves to `true` (instance prop wins over the theme default). This exists because a `UIListLayout` (which `VStack` always renders) unconditionally overwrites `Position`/`AnchorPoint` on every sibling it lays out each frame — there's no way to keep one child positioned independently while it stays parented inside that `VStack`. So instead:

- `Card` extracts at most one overlay `Card.Header` and one overlay `Card.Footer` out of `children` before they ever reach the `VStack`, and renders them as additional siblings of the `Box` inside an extra wrapping `frame` (`BackgroundTransparency={1}`, `ClipsDescendants={false}`, `AutomaticSize={Enum.AutomaticSize.XY}`) that takes over the `Position`/`AnchorPoint`/`ZIndex`/`LayoutOrder` the `Box` would otherwise have used (the `Box` itself is rendered with those four cleared, so it isn't positioned twice). `ClipsDescendants={false}` is what lets an overlay element visually protrude past the `Box`'s own edges (e.g. a plaque mounted above the top border).
- This extra wrapper is only introduced when at least one overlay header/footer is present — a card with no overlay sub-parts renders exactly as before (just the `Box`, or the centering `Container` + `Box` when `center` is set), so every theme that never sets `position.position` to `"absolute"` (`default`, `dark`, `sandstone`) is unaffected.
- When the instance sets any of its own `Position`/`AnchorPoint`/`top`/`left`/`right`/`bottom`/`center` fields, those fully take over the wrapper's placement (the theme's `position` is ignored in that case, aside from its `zIndex` still being available as a fallback) — the two vocabularies aren't merged field-by-field. Otherwise the wrapper's `Position`/`AnchorPoint` are derived from the theme's `position` object (see the field list below). `ZIndex` resolves from, in order: the instance's `ZIndex`, then the theme `position.zIndex`, then a default of `2` (one above the `Box`'s implicit `1`, so the overlay renders on top of it). A non-overlay header/footer ignores `position` entirely (position props on it have no visible effect, same as today, since it stays inside the `VStack`).
- When the theme's `position` sets `width` — or, when `width` is unset, sets both `left` and `right` — the header/footer's `Size` becomes fixed/relative-width, auto-height (`AutomaticSize={Enum.AutomaticSize.Y}`) instead of the default auto-width-and-height (`AutomaticSize={Enum.AutomaticSize.XY}`) every other header/footer still uses — this is what lets an overlay sub-part be narrower than the box it floats over (e.g. `wooden`'s footer, inset by a fixed amount on each side, rather than stretching to the box's full width). An explicit `width` always wins if both it and `left`+`right` are somehow set. When both `left` and `right` are set without an explicit `width`, the implied width is `100% - left - right` (standard CSS absolute-positioning behavior); this is purely a `Size` computation and doesn't change how `left`/`right` already drive `Position`/`AnchorPoint`. `width`/the `left`+`right` pairing has no effect at all outside overlay mode (an in-flow header/footer is always re-stretched to the `VStack`'s full width regardless, by `VStack`'s default Fill horizontal flex).
- The wrapper frame's own `center` is always ignored when deriving *its own* `Position`/`AnchorPoint` — when `Card` itself has `center={true}` (and no `Position`/`AnchorPoint`), centering is handled once by the outer centering `Container`/`uilistlayout` described above, exactly the same way `Box` always gets `center={undefined}` forced. This avoids centering being applied twice (once by the outer `uilistlayout`, once by the wrapper's own `AnchorPoint`), which would offset the wrapper by half its own size and let its overlay contents visually spill outside the card.
- Context/intent inheritance (`CardContext`) is unaffected by extraction — it flows through the React element tree, not the Roblox instance tree, so an overlaid header/footer still inherits the card-level `intent` normally.

### Overlay header/footer clearance

Pulling an overlay `Card.Header`/`Card.Footer` out of the `VStack` also removes it from layout entirely — nothing reserves vertical space for it inside the `Box`. Since the header is anchored at its offset (e.g. `wooden`'s `top: "-10px"`) and then grows *downward* from there to fit its own content, most of its rendered height typically overlaps down into the `Box`'s interior, directly over wherever `Card.Body`'s content starts — and symmetrically, an overlay footer anchored near the bottom (e.g. `wooden`'s `bottom: "-10px"`) grows *upward* from there, overlapping up into the `Box`'s interior. `Card` corrects for both by measuring the overlay header's/footer's actual rendered rect at runtime and reserving exactly that much extra top/bottom padding on the `Box`:

- The overlay header/footer reports its own `AbsolutePosition`/`AbsoluteSize` up to `Card` on every change, via a `Change` handler and a `reportOverlayHeaderRect`/`reportOverlayFooterRect` callback threaded through `CardContext` — the same measure-and-react-to-`Change` idiom `Accordion` uses for its expand/collapse height animation. Only a header/footer actually resolved to overlay mode reports; a non-overlay header/footer never does.
- `Card`'s overlay wrapper frame (see above) similarly reports its own `AbsolutePosition` and `AbsoluteSize` via `Change`; its position is equivalent to the `Box`'s top-left corner, and its position plus size gives the `Box`'s bottom edge, since the `Box` always renders at `Position (0, 0)` filling that wrapper once `hasOverlay` clears its position props.
- Once both measurements are available for a given side, `Card` computes:
  - Header: `max(0, (header's AbsolutePosition.Y + header's AbsoluteSize.Y) - wrapper's AbsolutePosition.Y)` — how far the header's bottom edge extends past the box's top edge.
  - Footer: `max(0, (wrapper's AbsolutePosition.Y + wrapper's AbsoluteSize.Y) - footer's AbsolutePosition.Y)` — how far the footer's top edge sits above the box's bottom edge (`AbsolutePosition` is always a rect's top-left corner regardless of `AnchorPoint`, so this is exactly the upward overlap).

  Each is applied as the `Box`'s top/bottom padding respectively (`resolvedPadding`, taking over the zero padding `spacing="None"` would otherwise force). This is generic to whatever the header/footer actually renders (text size, wrapping, icon, custom children) rather than a fixed value tuned for one theme.
- The result is `0` (i.e. no layout change) on either side whenever that header/footer doesn't overlap the box at all, and — for one frame around mount, before the first `Change` events fire — while unmeasured; this settle-after-mount characteristic is the same tradeoff `Accordion` already accepts for its own runtime measurements.
- Header and footer clearance are computed and applied independently — either, both, or neither can be nonzero depending on which overlay sub-parts are present and how far they overlap.
- **Footer-absent bottom floor**: when there's no `Card.Footer` at all (`overlayFooter === undefined`), `footerClearance` has nothing to measure and is always `0` — in that case `Card` instead floors the `Box`'s bottom padding at `theme.components.box.padding`'s explicit bottom inset, via `SpacingHelper.GetExplicitPadding(theme.components.box.padding, theme.default.spacing)` (a tier-3-only lookup with **no** fallback to the global `theme.spacing` scale). This exists so a theme that gives `Box` a real `padding` for a decorative background image (e.g. `wooden`'s wood-frame 9-slice art, `padding: "35px 40px 40px 40px"`) still keeps its content clear of that border even without a footer to reserve the space via overlap. Themes that never set an explicit `theme.components.box.padding` resolve this floor to `0`, so they're unaffected. Critically, this floor is skipped entirely whenever a `Card.Footer` **is** present — `footerClearance`'s real measured overlap is used as-is in that case, unchanged from before, so a themed footer's own reserved space is never padded further on top of it.

## Theme

Card defaults live under `theme.components.card`:

- `cornerRadius` — corner radius applied to the header's top corners and the footer's bottom corners.
- `borderThickness` — shared fallback border stroke thickness for the header/footer, used whenever that section's own `header.borderThickness`/`footer.borderThickness` (below) is unset.
- `header.borderThickness` / `footer.borderThickness` — optional per-section override of the border stroke thickness; falls back to `borderThickness` above when unset. Unset in every shipped theme today.
- `header.spacing` / `header.padding` / `header.intents` — header padding (tier 2 `ScaleSizeValue<number>` / tier 3 `ScaledCssPadding`, resolved through the shared [padding resolution](../index.md#padding-resolution) and pinned to the `"md"` scale key regardless of `theme.default.spacing` — an instance `spacing` prop still overrides the active key), and per-intent header colors. Each intent's `IntentScheme` can also set `backgroundImage` (a `Partial<CssBackgroundImage>`, merged field-by-field the same way as everywhere else `ColorHelper.getIntentColors` is used), which `Card.Header` renders via `Container`'s own `backgroundImage` prop.
- `footer.spacing` / `footer.padding` / `footer.intents` — same as `header.spacing`/`header.padding`/`header.intents` above, mirrored for the footer.
- `body?.spacing` / `body?.padding` — `Card.Body`'s own tier 2 (`ScaleSizeValue<number>`) / tier 3 (`ScaledCssPadding`) padding overrides, resolved independently of `theme.components.box.padding`. Both are unset in every shipped theme today, so `Card.Body`'s padding falls through to the global `theme.spacing`/`theme.default.spacing` scale-token system, following `theme.default.spacing` dynamically — unlike `header`/`footer`, which always pin `"md"`. Every shipped theme's `default.spacing` is `"md"` today, so this isn't currently a visible difference, but a theme that changes `default.spacing` will now shift `Card.Body`'s default padding independently of `Card.Header`/`Card.Footer`'s (previously all three used a hardcoded `"md"`, unaffected by `theme.default.spacing`).
- `header.position` / `footer.position` — optional `CssPosition` (from `theme.style.ts`) controlling overlay placement for that sub-part: `position?: "static" | "absolute"` (only `"absolute"` triggers overlay mode), `top`/`left`/`right`/`bottom` (`CssSize`), `center?: boolean | "x" | "y"` (unlike `PositionElementProps`' boolean-only `center`, this can center a single axis while `top`/`left`/`right`/`bottom` still positions the other), `width?: CssCalcSize` (fixed/relative width, height stays auto-sized — see above; only meaningful in overlay mode; when unset but both `left` and `right` are set, a width is implied automatically as `100% - left - right`, mirroring standard CSS), and `zIndex?: number` (default `2` when overlay is on). Unset in `default`/`dark`/`sandstone`; the `wooden` theme sets `header.position` (`{ position: "absolute", center: "x", top: "-10px", zIndex: 2 }`) to mount the header as a plaque centered horizontally above the box's top edge, and `footer.position` (`{ position: "absolute", bottom: "-10px", left: "50px", right: "50px", zIndex: 2 }`) to mount the footer as a plaque below the box's bottom edge, inset 50px on each side — equal `left`/`right` insets implicitly center it and imply a width 100px narrower than the box, the same rendered result as an explicit `center: "x"` + `width: "100% - 100px"` would have produced.
- `CssSize` (used by `top`/`left`/`right`/`bottom` above) accepts a plain number/`"Npx"`/`"N%"`/`"N"`. `CssCalcSize` (used by `width` only) additionally accepts the one CSS `calc()` shape supported anywhere in this codebase — a percent term plus/minus a pixel term, e.g. `"100% - 50px"` — which maps directly onto `UDim(scale, offset)`. This is a distinct, wider type from `CssSize` specifically so that `CssSize`'s far more common uses (composed multiple times over into `CssQuad`/`CssDual` for padding/shadow/etc.) aren't widened along with it, which was found to blow past TypeScript's template-literal complexity limit at unrelated call sites.

## Story

A story should demonstrate a card with header, body, and footer using the card-level `intent`, plus a header (or footer) whose own `intent` overrides the card-level one, and (given the `wooden` theme exists in this package's theme switcher) a story/demo that cycles themes should show the header's overlay "mounted plaque" look when `wooden` is selected — and, now that `wooden` also overlays the footer, should show the footer's narrower, centered, bottom-flush plaque at the same time (both use the same underlying overlay mechanism, so one story exercising both is sufficient — no need for a separate footer-only story).
