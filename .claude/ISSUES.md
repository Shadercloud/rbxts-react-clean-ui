# Issues

Design/spec-vs-implementation inconsistencies and likely bugs found while back-propagating the component specifications under `.claude/specifications/components/` from the existing `src/Components/` source (2026-08-25). Each entry names the affected component, what's inconsistent, and where it's documented as current (not intended) behavior in the spec. Check items off as they're resolved; when a fix changes the intended behavior, update the corresponding spec file in the same change.

## Input

- [ ] **Select** — `Select.Option`'s `BackgroundColor3` prop is accepted but never applied; the rendered background always comes from `ColorHelper.getIntentColors(...)`. Contradicts `docs/content/docs/components/form/select.mdx`, which shows `BackgroundColor3` as a working customization. See `.claude/specifications/components/input/select.md`.
- [ ] **Button** — `fontWeight` prop is declared on `ButtonProps` but never read anywhere. See `.claude/specifications/components/input/button.md`.
- [ ] **Button** — doesn't use the shared `HoverButton` primitive; rolls its own `MouseEnter`/`MouseLeave` state instead, despite the general convention (`.claude/specifications/components/index.md`) that hover-aware controls should. See `.claude/specifications/components/input/button.md`.
- [ ] **Checkbox** — mixes two independent intent-theming systems: background color/transparency come from `theme.components.button` keyed by the generic `intent` prop, while border/icon colors come from `theme.components.checkbox.intents` keyed by `intent-checked`/`intent-unchecked`. See `.claude/specifications/components/input/checkbox.md`.
- [ ] **Checkbox** — `theme.components.checkbox.borderColor`/`.borderThickness` are declared in `src/Theme/theme.template.ts` but never read; the component sources those visuals elsewhere. See `.claude/specifications/components/input/checkbox.md`.
- [ ] **Checkbox** — `onChange` fires once on mount (its effect runs with the initial `checked` value immediately), not only on user-driven toggles. See `.claude/specifications/components/input/checkbox.md`.
- [ ] **Checkbox / wooden theme** — because Checkbox borrows `theme.components.button.backgroundTransparency` and `.borderThickness` (see the mixed-theming-system entry above) rather than having its own fields, and `wooden.theme.ts`'s `button` block sets both to `1`/`0` (buttons rely entirely on a background image, which Checkbox never renders), an unchecked checkbox in the wooden theme currently renders with **no visible fill and no visible border at all** — not merely an "outline-only" look. A checked box similarly has no fill/border, just the checkmark icon floating with no boundary. Fixing this properly likely means giving Checkbox its own dedicated background-transparency/border-thickness theme fields instead of borrowing Button's. See `.claude/specifications/components/input/checkbox.md` and `src/Theme/themes/wooden.theme.ts`.
- [ ] **Slider** — inherits `ContainerProps.group` but never reads it (builds its root frame by hand instead of through `Container`), so `group` is inert. See `.claude/specifications/components/input/slider.md`.
- [ ] **Input** — the `"Alphanumeric"` and `"Email"` validations (`CHARACTER_ALLOW_LIST_PATTERNS` in `Input.validation.ts`) use the Lua class `%w`, which matches ASCII letters and digits only, per byte. Any accented, Cyrillic, CJK or other multi-byte character is rejected and the box reverts to the last valid text, so `"Alphanumeric"` cannot be used for names in most languages. Nothing is corrupted. A Unicode-aware allow-list needs a decision on what counts as a letter, so it was left as is (found in the 2026-11-17 non-English text audit). See `.claude/specifications/components/input/input.md`.

## Layout

- [ ] **Container** — the `group`-derived default width only has a visible effect when the consumer also supplies an explicit `AutomaticSize` that excludes `X` (e.g. `"None"`/`"Y"`); otherwise the default `AutomaticSize: XY` (used whenever `width`/`height` are both omitted) overrides the pixel width on the `X` axis, making `group` sizing silently inert in the common case. See `.claude/specifications/components/layout/container.md`.
- [ ] **FlexItem** — combining `group: true` (inherited via `Container`) with `FlexItem` likely breaks flex behavior: `Container` wraps `children` in `Group.Element` when `group` is set, which would move `FlexItem`'s `UIFlexItem`/`UIListLayout` onto `Group.Element`'s inner measurement frame instead of the outer frame actually placed inside the parent's `UIListLayout`, very likely making `mode`/`GrowRatio`/`ShrinkRatio` stop working. See `.claude/specifications/components/layout/flexitem.md`.
- [ ] **HStack / VStack** — for the same `spacing` value, `HStack` applies `ceil(padding / 2)` pixels between children while `VStack` applies the full padding value — likely an unintentional asymmetry rather than a deliberate design choice. See `.claude/specifications/components/layout/hstack.md` and `layout/vstack.md`.
- [x] **Scroller / `SizeHelper.GetSize`** — *Resolved 2026-11-23:* the tests were wrong, not the component. The Scroller spec says decorated Scrollers need an explicit or parent-relative size, `GetSize` has used its default only when both axes are unset since it gained one, and the tests never set a width; `tallScroller` now passes `width="100%"` and the window width is asserted too. — `ScrollerSizeConstraint` (`src/Tests/Components/Layout/Scroller.constraint.test.tsx`) fails three tests (`maxHeightScrolls`, `minHeightScrolls`, `noChromeWithoutTheme`) with "Timed out waiting for a GuiObject named "Scroller" to render with a non-zero AbsoluteSize". They mount `<Scroller height={...} minHeight/maxHeight={...}>` with no `width`, and `GetSize` turns the unset axis into `UDim(0, 0)`, so the Scroller is 0px wide. Neither the test nor the helper changed in the 2.2.0 Scroller gutter work (found 2026-11-23). Needs a decision: give the tests `width="100%"`, or make `GetSize` fall back per axis the way `ProgressBar`/`Slider` do. See `.claude/specifications/components/layout/scroller.md`.
- [ ] **Scroller** — the Scroller spec's implementation notes assume `CanvasPosition` is in the ScrollingFrame's own (unscaled) units. Studio measurements made for Textarea (2026-11-25) show it is in screen pixels under any ancestor `UIScale`: at scale 1.5, a 1024 design-px canvas in a 160 design-px window scrolls to a max `CanvasPosition.Y` of 1296 (= (1024 − 160) × 1.5). `updateThumb`/`updateNearEnd` divide `AbsoluteWindowSize`/`AbsoluteCanvasSize` by `useUiScale()` but mix in the raw `CanvasPosition`, so under a `UiScaleRoot` with a scale other than 1 the custom `ScrollerThumb` offset and the `onNearEnd` distance are off by the scale factor. Textarea converts `CanvasPosition` itself. See `.claude/specifications/components/layout/scroller.md` and `input/textarea.md`.
- [ ] **Draggable** — the `React.forwardRef<Frame, ...>` ref parameter is never attached to any rendered instance, so a consumer's ref is silently dropped. See `.claude/specifications/components/layout/draggable.md`.
- [ ] **Draggable** — the `Placeholder`'s theme-driven `backgroundTransparency` is immediately overridden by a hard-coded `BackgroundTransparency={0.3}` at the call site, so `theme.components.draggable.placeholder.backgroundTransparency` currently has no visible effect. *(Corrected 2026-09-18: it's the other way round. `Placeholder` spreads `{...props}` before its own `BackgroundTransparency`, so the theme value wins and the call site's `0.3` is dead. Either way one of the two values is ignored.)* See `.claude/specifications/components/layout/draggable.md`.
- [x] **Draggable / Droppable** — *Resolved 2026-09-18:* droppables are now hit-tested from a shared registry, only the topmost target as drawn wins, and `onDrop` fires once on release. — drop-target detection notifies **every** overlapping registered `Droppable` at the pointer position via `onDrop`, but the single `DroppableRegistration` reported back through `Draggable`'s `onDragged`/`onDropped` is whichever was processed last (lowest `ZIndex`), not necessarily the top-most visual match — an asymmetry between "many `onDrop` calls" and "one reported registration" that doesn't implement clean top-most-wins semantics. See `.claude/specifications/components/layout/draggable.md` and `layout/droppable.md`.
- [ ] **Fieldset** — `FieldsetContextValue.disabled` is threaded through context but read by nothing (`Fieldset.Label`, `Fieldset.Control`, `Checkbox`, `Input`, `Select` all ignore it) — setting `disabled` currently has zero observable effect. See `.claude/specifications/components/layout/fieldset.md`.
- [ ] **Tabs** — several theme fields declared in `theme.template.ts` are dead: top-level `theme.components.tabs.backgroundColor` and `tabs.list.borderColor`/`.borderThickness` are never read. *(Updated 2026-09-13: `tabs.button.borderThickness` is now read, `tabs.button.cornerRadius` is read in its per-corner object form (the scalar form is still ignored), and top-level `tabs.cornerRadius` is read by `Tabs.Body`.)* See `.claude/specifications/components/layout/tabs.md`.
- [x] **Container / Gradient** — *Resolved 2026-09-11:* `CssHelper.resolveBackgroundGradient` now accepts the partial and returns `undefined` for unset/empty `colors`, and `Gradient` no longer casts. — the spec says that when `backgroundGradient` is unset "(or `colors` is unset), `Gradient` renders nothing", but `Gradient` casts its `Partial<CssBackgroundGradient>` to the full type and `CssHelper.resolveBackgroundGradient` has no `colors` guard. A defined gradient without `colors` errors in `buildColorSequence` instead of rendering nothing. An empty `colors: []` array errors the same way (`keypoints[0]` is nil). See `.claude/specifications/components/layout/container.md`, `.claude/specifications/components/decorator/gradient.md` and `.claude/architecture/shared-modules.md`.
- [x] **Tabs** — *Resolved 2026-09-13:* `Tabs` now accepts `value`/`onValueChange`. — has no controlled `value`/`onValueChange` API (uncontrolled-only), unlike `Accordion`'s equivalent controlled/uncontrolled support. Documented as an intentional API difference for now, but worth a deliberate decision rather than an unexamined gap. See `.claude/specifications/components/layout/tabs.md`.
- [x] **Min and max size (`SizeElementProps`)** — *Resolved 2026-11-09:* `components/index.md`, `layout/table.md`, `typography/text.md`, `surface/progressbar.md` and `shared-modules.md` now say maximums only cap explicit or `%` sizes (plus a `TextLabel`'s own wrapped text). — `.claude/specifications/components/index.md` ("Min and max size") says `maxWidth`/`maxHeight` clamp the resolved size "whatever produced it (`Size`, `width`/`height`, `%`, or `AutomaticSize`)". In Studio, a `UISizeConstraint` `MaxSize` does not limit `AutomaticSize` growth driven by child frames: a native `Frame` with `AutomaticSize.XY`, `MaxSize` 80x30 and a 120x80 child still lays out at 120x80, and so does an auto-sized `Container` with `maxWidth`/`maxHeight`. `MinSize` does raise auto-sized elements. This is an engine limit, not a component bug, so the spec (and any docs that promise it) should say maximums only apply to explicit or `%` sizes. See `.claude/specifications/testing.md` → "Min and max size".
- [ ] **Scroller / UiScaleRoot** — under a `UiScaleRoot`, `Scroller`'s custom thumb and `onNearEnd` treat `ScrollingFrame.CanvasPosition` as unscaled (design-pixel) units while dividing `AbsoluteCanvasSize`/`AbsoluteWindowSize` by the scale. That matches how `CanvasSize` offsets behave, but it was not verified in Studio when global UI scaling was added (2026-11-23). If `CanvasPosition` turns out to be in screen pixels under a `UIScale`, the thumb runs ahead of the content and `onNearEnd` fires early by the scale factor. Behaviour at scale `1` is unaffected either way. *(Updated 2026-11-25: measured in Studio while building `Textarea`: `CanvasPosition` is in screen pixels under a `UIScale` (a 1000 px canvas in a 100 px view scrolls to a max of 1350 at scale 1.5), so this bug is real. See the scale table in `.claude/specifications/components/input/textarea.md`.)* See `.claude/specifications/components/layout/scroller.md`.

## Navigation / Surface / Chart

- [ ] **Menu** — `MenuItem` extends `ButtonProps` and its `.mdx` doc claims `intent` and "all other Button props" are supported, but the JSX only forwards `title`, `icon`, and `Event` to the underlying `Button` — `intent` and everything else is silently dropped. See `.claude/specifications/components/navigation/menu.md`.
- [ ] **Pie** — the hide-labels prop is read as `props['Label-hidden']` (capitalized), while docs and convention suggest `label-hidden` (lowercase) — the documented lowercase prop has no effect. See `.claude/specifications/components/chart/pie.md`.
- [ ] **Pie** — no zero-total-value guard: if all values are `0` or the data array is empty, `value / totalValue` divides by zero, producing `NaN` proportions with undefined rendering behavior. See `.claude/specifications/components/chart/pie.md`.
- [ ] **Pie** — `PieProps`/`PieValue`/`PieLabel` are not exported, despite `PieProps` being the component's public prop surface and `chart/index.md` calling for chart-specific public-API interfaces to be exported. See `.claude/specifications/components/chart/pie.md`.
- [ ] **Pie / Icon** — dead theme fields: `theme.components.charts.pie.hoverDarken` is declared but `Pie` hard-codes a `0.2` default via its own `hover-darken` prop instead; `theme.components.box.intents`, `theme.components.tooltip.cornerRadius` (Tooltip actually uses `theme.components.button.cornerRadius`), and `theme.components.toast.body.typography` are similarly declared but never read. See `.claude/specifications/components/chart/pie.md`, `interaction/tooltip.md`, `interaction/toast.md`, `surface/box.md`. (`theme.components.card.borderThickness` was previously listed here too, but `Card.Header`/`Card.Footer` now read `theme.components.card.header/footer.borderThickness ?? theme.components.card.borderThickness`, so it's live — see `surface/card.md`.)
- [ ] **Icon** — `SpinningIcon`'s tween-start effect has no dependency array, so `setGoal(360); tween.start()` re-runs on every render rather than once at mount. Likely harmless since the animation loops forever, but worth confirming against `useTween`'s intended usage. See `.claude/specifications/components/surface/icon.md`.
- [ ] **Tooltip** — `TooltipProps` extends `BoxProps` and `interaction/tooltip.md` says the inherited size props style the popup surface, but `TooltipPopup` never reads `Size`/`width`/`height` (its canvas group and `Content` frame are always auto-sized), so they, and the new `minWidth`/`maxWidth`/`minHeight`/`maxHeight`, have no effect. A `maxWidth` that wraps long tooltip text would be useful but needs `Text` wrapping under an auto-sized parent, which wasn't verified. See `.claude/specifications/components/interaction/tooltip.md`.
- [ ] **Toast** — `dismiss()`/`dismissAll()` skip the fade-out animation; only self-triggered dismissal (timeout expiry or the close button) fades out. This looks intentional but is easy to mistake for an inconsistency — worth confirming it's deliberate. See `.claude/specifications/components/interaction/toast.md`.
- [x] **ProgressBar** — *Resolved 2026-11-09:* the track and the header wrapper now fall back per axis (width to `100%`, track height to the theme/`scale` height), like `Slider`. — the track's `Size` is `SizeHelper.GetSize(props, new UDim2(new UDim(1, 0), height))`, and `GetSize` only uses that default when both `width` and `height` are unset. So `<ProgressBar width="50%" />` gets a 0 px tall track, and `height` alone gets a 0 px wide one. This contradicts `.claude/specifications/components/surface/progressbar.md` ("only the height is theme/`scale`-driven by default"). `Slider` had the same bug and now falls back per axis (see `.claude/specifications/components/input/slider.md` → Implementation notes). No current scene or story sets only one axis on a ProgressBar.
- [x] **Text** — *Resolved 2026-11-17:* the test was wrong, not the component. Plain `shrinkToFit` text settles on its first frame at 54px in the 60px slot and stays there, because the next width the engine renders is 61px; the Text spec allows a fit up to one text-size step short. The `plain` row now uses `assertWidestFit` (see `.claude/specifications/testing.md`). — the Studio test `TextShrinkToFit.shrinksIntoSlot`, row `plain`, fails with "expected the visual width 54 to fill about 60px" (the `spaced` row passes). Found 2026-11-17; it fails identically against the 2.1.1 `Text.tsx`, so it predates the non-English text change. Not yet determined whether plain `shrinkToFit` text really settles about 6px short of the slot or the test reads the width before the shrink search settles; check the Text story before changing either.
## Shared modules

- [ ] **Theme / TypographyHelper** — `TypographyStyle.font` is typed `Enum.Font` and `TypographyHelper.toFontFace` only accepts an `Enum.Font`, so a theme can only pick fonts that exist in that enum. A game cannot point the theme at a `Font` object (`new Font("rbxasset://fonts/families/....json")` or `Font.fromId(...)`), which is how families that are not in `Enum.Font` are loaded. Switching between `Enum.Font` values per language at runtime works. Accepting `Enum.Font | Font` would be a public type change across the theme, `Text`, `Input` and `toFontFace`, so it was not done in the 2026-11-17 non-English text change.
- [ ] **Theme** — there is no single theme-wide font field: each of the six `theme.typography.*` styles carries its own `font`, so changing the font means overriding all six.
- [ ] **testing.md / VStack** — `.claude/specifications/testing.md` → "Values coupled to DefaultTheme" says HStack/VStack gaps are half the resolved spacing (`math.ceil(GetPadding / 2)`), giving 6 and 12, but `VStack.tsx` sets its `UIListLayout.Padding` to `SpacingHelper.GetPadding(theme, props.spacing)` directly. Found 2026-11-25 while writing `Textarea.stack.test.tsx`, which reads the gap from the rendered layout instead. Check `HStack.tsx` too, then correct the note (or the components, if halving was intended).

- [x] **ColorHelper** — *Resolved 2026-09-11:* `mergeLayers` now merges `backgroundGradient` field by field. — `components/index.md` says `backgroundGradient` merges field by field across intent/state layers, like `backgroundImage` and `typography`. But `ColorHelper.mergeLayers` only merges those two, so `backgroundGradient` is last-wins. A layer that sets only part of a gradient (the spec's own example is a `hover` layer that sets just `backgroundGradient.rotation`) replaces the whole gradient and drops `colors`. Combined with the missing `colors` guard above, that would error at render. See `.claude/specifications/components/index.md` and `.claude/architecture/shared-modules.md`.
